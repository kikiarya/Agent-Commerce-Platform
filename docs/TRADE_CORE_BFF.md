# Storefront → Trade Core 契约

浏览器使用前台 JWT；Express 从登录身份取得核心账号关联，解密 Store 颁发的 JWT 并以 Bearer 转发。不会使用客户端 userId、X-User-Id、默认用户 1 或前台签名密钥冒充核心用户。

## 身份

- `GET /api/auth/core-link` 查询关联/登录有效性。
- `POST /api/auth/core-link` 提交 `{username,password}` 到核心登录。BFF 不保存密码、不向浏览器返回核心 JWT。
- `core_account_links` 一对一关联，已有用户不能切换 Core 身份。登出清除核心令牌但保留映射。
- 核心令牌 AES-256-GCM 加密存入 SQLite；使用 `CORE_TOKEN_ENCRYPTION_KEY`，未设置时从前台 JWT 密钥派生。密钥至少 32 字节。更换密钥后需要重新登录，不能据此宣称完整密钥管理。
- 旧 `user_id_map` 保留备查，不自动认证；需要本人验证核心账号。历史共享用户 1 的订单需人工核对，不能批量认领。

## 结算

全部接口要求前台登录，并校验 `core_checkout_owners` 中的归属。

| 接口 | 输入/语义 |
| --- | --- |
| POST /api/checkout | items 1–100 行，正整数 quantity，不重复 SKU；shippingAddress |
| GET /api/checkout/:id | 状态、报价版本、持久化 idempotencyKey |
| PUT /api/checkout/:id | 修改商品/地址，核心清除旧报价确认 |
| POST /api/checkout/:id/quote | 生成报价 |
| POST /api/checkout/:id/confirm | `{quoteVersion}` 必须是展示给用户的版本 |
| POST /api/checkout/:id/complete | `{quoteVersion}`，使用服务端持久化键；提供不同键返回 409 |

核心目录的商品使用显式 skuId。本地 product_id/phone_id 必须经过 product_sku_map；默认不假定两个数据库主键相同。浏览器不传 bankMock。

UI 保存结算 ID、幂等键、报价版本和购物车快照用于刷新重试；先展示商品单价、数量、运费、总价与地址，再请求确认。网络不明时不创建新结算。已完成结算可再次 complete 修复 SQLite 订单投影。同一浏览器更改购物车后恢复旧结算，不会清掉新购物车。

关闭 USE_TRADE_CORE 只禁止创建新核心结算；已创建结算、核心订单读取/取消仍走 Store。核心商品不能落入本地下单。订单详情和客服核心订单查询使用实时核心结果，失败明确返回不可用；列表的核心记录标记 stale_projection，需查详情刷新。

## 范围与限制

SQLite 投影不是交易事实来源。核心提交成功、BFF 投影失败时，用同一结算重试修复；尚无后台投影对账任务。浏览器清理本地存储或换设备后，登录同一个商城账号，通过 /orders.html 读取服务端归属记录恢复结算。创建核心结算后 BFF 意外退出可能留下未确认的孤立结算，不会因此自动扣款。

账号关联是过渡方案，不是统一 SSO。历史结算没有 BFF 归属记录时拒绝访问，需要核对后补录。旧库数据、商品映射、Redis 秒杀数据没有在此次代码迁移中自动合并。客服仍为关键词 FAQ/规则工具，未实现自主 Agent 交易闭环。回调、WebSocket/gRPC 与公网部署安全不在此次验收范围。

## P0 订单与结算恢复

首页我的订单入口为 /orders.html。GET /api/checkout 按当前身份分页读取服务端结算记录，每页 20 条。核心读取失败的记录标记 unavailable，不显示伪造状态。列表读取没有交易副作用。页面支持交易账号重新登录、查询实时订单状态、重新核对并恢复结算，以及找回已完成但本地投影缺失的订单。恢复使用服务端原幂等键，不依赖浏览器保存的报价。

订单列表暂显示最近 50 条本地记录；详情手动刷新读取实时核心状态。订单详情通过鉴权接口读取已保存的配送事件，按发生时间展示包裹进度；支持手动刷新，尚无自动轮询。没有 BFF 归属记录的历史结算不自动认领。Node 回归 19 项、Store 测试 41 项通过。浏览器已在独立内存数据库和模拟 Core 上验证重新登录、无本地缓存恢复、报价确认、订单生成与配送事件展示，未发现控制台错误。真实 Docker 全链路尚待完成。
配送历史：Store `GET /api/orders/{coreOrderId}/delivery-events` 在读取事件前校验订单归属；BFF `GET /api/orders/{localOrderId}/delivery-events` 先校验前台身份与本地订单归属，再转发核心凭据。事件包含 shipmentId、status 和 occurredAt，空列表表示尚无记录，接口失败显示不可用，不伪造进度。

页面验收环境可运行 `node scripts/preview-orders.cjs`，按输出的本机地址打开。仅含预置测试身份、内存 SQLite 和模拟 Core，退出后数据消失，不用于真实联调或部署。
## P1 导购第一步

聊天支持例如 `推荐滑板，预算100元`、`推荐 wheels 100元以内`。核心模式调用 Store `/api/products/search` 并要求 inStock=true，读取当次商品数据，按价格排序和预算上限筛选；返回结构化 shopping 字段与文字结果。本地模式读取本地可售商品。没有商品、服务不可用、资料不足分别显示，不能把旧目录当作核心查询降级结果。

这是支持规则解析与可选模型工具选择的只读导购，不是已完成的交易 Agent。明确预算、名称查询和会话内条件修改已实现；丰富属性比较和对话创建待确认订单尚未实现。用途仅记录并提示资料不足，不保证性能。当前只处理人民币单价上限，不含运费；复杂排除条件和范围请求要求澄清。商品结果通过确定性文案展示，不交给模型改写价格或添加性能承诺。

验证：Node 26 项测试通过，包括聊天路由真实 HTTP 模拟核心的只读查询验证。尚无真实模型或完整服务部署验证。
### 导购会话条件

同一会话支持先说 `推荐滑板，预算200元`，再说 `预算降到100元`、`换成轮子`、`用于通勤`、`不限预算`。`重新选`、`重新开始`、`清空偏好`清空条件。回复展示当前生效的名称和单价上限。未知排除条件要求澄清，不覆盖此前条件。

SQLite shopping_preferences 按已校验归属的 session_id 保存筛选条件，不缓存商品价格或库存，每轮重新查询商品。24 小时不更新后不再沿用旧条件；以用户消息序号防止慢请求覆盖更新的条件。跨账号使用他人的会话 ID 会分配新会话，不继承偏好。匿名会话仍以随机会话 ID 为访问凭据，不应存敏感个人资料。

Node 回归现为 34 项通过，包含模拟模型响应的工具白名单、参数校验、预算约束和故障回退验证。真实模型接口及 Docker 全链路尚未联调。
### 可选模型导购

设置 SHOPPING_MODEL_ENABLED=true，并配置 LLM_PROVIDER、LLM_API_KEY；可通过 LLM_BASE_URL 与 LLM_MODEL 指定兼容接口。根目录 Compose 已透传这些变量。默认关闭，不配置密钥时使用规则。供应商必须支持 function calling，本次未验证各供应商的实际兼容性。

每轮最多请求一次模型，只允许 search_catalog（商品名称查询）或 ask_clarification（追问）。工具参数严格校验，不能修改程序解析的预算，也不暴露身份、下单或支付工具。模型选择搜索后，程序查询业务接口并再次筛选预算，使用固定格式展示真实价格。8 秒超时、接口异常或非法工具返回会回退规则；交易核心不可用时不会改用本地商品冒充结果。

JSON 与 SSE 完成事件均返回 shopping；mode 区分 model-catalog-guidance、catalog-guidance 和 catalog-guidance-fallback。模型参与范围是查询选择与追问，商品事实由接口提供。当前路由仅覆盖已识别的导购请求，不能据此声称所有自由对话均有事实依据。

下一步按顺序补：对话中的商品/数量整理与待确认报价卡片；带可阅读出处的退换货、配送、保修问答；异常处理与安全重试；独立 Agent 场景评测。真实服务、真实模型联调仍是单独的验收项。
